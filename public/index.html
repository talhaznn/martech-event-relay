MarTech Event Relay

Eine Konversion, zwei Wege. Der Browser meldet sie über den Google Tag Manager an GA4. Parallel geht dieselbe Konversion an einen Cloudflare Worker, der sie serverseitig an das Measurement Protocol und an einen Empfänger in der Form der Meta Conversions API weiterreicht. Beide Wege tragen dieselbe event_id.

Worker wird geprüft Tag Manager GA4 client_id

Konversion auslösen

Warum der zweite Knopf. Er schickt die vorherige Anfrage unverändert noch einmal, mit derselben event_id. So sieht ein doppelter Klick oder ein Wiederholversuch nach einem Netzwerkfehler aus. Der Relay erkennt das und leitet nicht erneut weiter.

Warum die beiden Ereignisse verschieden heißen

Der Browser schickt über den Tag Manager demo_conversion an GA4. Der Worker schickt demo_conversion_server. Beide tragen denselben Parameter event_id.

Das ist Absicht. Meta dedupliziert Browser- und Serverereignis anhand von event_id und event_name selbst. GA4 tut das nicht. Wer dieselbe Konversion unter demselben Namen einmal über den Tag Manager und einmal über das Measurement Protocol schickt, hat sie in GA4 zweimal.

Deshalb unterscheiden sich hier die Namen, und die Zusammengehörigkeit hängt am gemeinsamen Parameter. In DebugView stehen beide nebeneinander und lassen sich über die event_id derselben Anfrage zuordnen. Die Deduplizierung, die GA4 nicht mitbringt, übernimmt der Relay: dieselbe event_id kommt kein zweites Mal durch.

Arbeitsprobe von Talha Zengin. Quelltext unter github.com/talhaznn/martech-event-relay. Alle Eingaben sind Beispielwerte, es werden keine Daten gespeichert. Der werbliche Empfänger ist nachgebildet und spricht nicht mit Meta.
